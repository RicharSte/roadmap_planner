# Как работать с Claude Code и OpenCode в этом проекте

Цель — **запускаемый MVP** (`.dmg` для macOS, затем Windows), который можно передать и использовать.
Конец работы определён заранее: [`docs/mvp-done.md`](mvp-done.md). Когда все пункты отмечены — проект готов.

## 1. Цикл одной задачи

```
 /task-next ──► /task-plan T-XXX ──► [Ревью плана в Plannotator] ──► /task-build T-XXX
                                         ▲  замечания  │ approve          │
                                         └─────────────┘                  ▼
                       коммит ◄── [Ревью кода в Plannotator] ◄── отчёт docs/reports/T-XXX.md
                         │              ▲ замечания │
                         ▼              └───────────┘
                   handoff → /task-next (другой агент)
```

| Шаг                | Что делаешь ты                                                                                                       | Что делает агент                                                                                                              |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 1. Задача          | Запускаешь `/task-next` в любом инструменте                                                                          | Читает `docs/handoff.md` и backlog, говорит: какая задача, каким инструментом/моделью, какая команда                          |
| 2. Интервью + план | Запускаешь `/task-plan T-XXX`, отвечаешь на вопросы, пока не закрыты все решения                                     | Если задача требует решений — проводит интервью (`grilling`), затем пишет `docs/plans/T-XXX.md` и открывает его в Plannotator |
| 2a. Ревью плана    | Читаешь план в браузере, оставляешь замечания или жмёшь **Approve**, затем нажимаешь **Send Feedback**               | Получает feedback из Plannotator: правит план (до 2 кругов) или помечает `approved`                                           |
| 3. Реализация      | Запускаешь `/task-build T-XXX` (обычно в OpenCode)                                                                   | Делает ровно план, пишет тесты, запускает проверки                                                                            |
| 4. Объяснение      | —                                                                                                                    | Пишет `docs/reports/T-XXX.md` и открывает изменения кода в Plannotator                                                        |
| 4a. Ревью кода     | Читаешь отчёт и diff, задаёшь вопросы прямо на строках кода или жмёшь **Approve**, затем нажимаешь **Send Feedback** | Получает feedback из Plannotator, отвечает на замечания и правит (до 2 кругов)                                                |
| 5. Передача        | Делаешь коммит по предложенному сообщению и при желании `git push`                                                   | Отмечает задачу `done`, обновляет `docs/handoff.md`: следующая задача, инструмент, команда                                    |

Новую задачу лучше начинать в **новой сессии** (`/clear` в Claude, новая сессия в OpenCode).

## 2. Кто что делает

В backlog у каждой задачи две колонки — кто планирует и кто реализует:

- **C** — Claude Code (Pro). Планы для архитектуры, данных, Rust, хранения; сложные баги.
- **K** — OpenCode + Kimi K2.7 Code. Реализация планов, планы простых UI-задач.
- **M** — OpenCode + MiniMax M3 или слабее. Каркас, мелкий UI, документация.

Модель в OpenCode выбираешь сам перед запуском команды. Для задач с Rust и хранением данных
(T-005, T-006, T-010, T-011) после ревью кода можно дополнительно запустить `/review-diff T-XXX` в Claude.

## 3. Как читать план

План всегда отвечает на три вопроса — именно это ты проверяешь на ревью:

1. **Проблема** — что сейчас не так и зачем это нужно для MVP.
   (Перед решением — раздел «Решения из интервью»: твои ответы, на которых построен план.)
2. **Решение** — подход простыми словами и почему так.
3. **Критерии приёмки** — чек-лист, по которому видно, что задача выполнена.
   Каждый пункт проверяемый: команда, тест или ручной шаг с ожидаемым результатом.

Дальше идут файлы (не больше 6), шаги, тесты, «Вне рамок» и риски. Шаблон: [`docs/plans/_template.md`](plans/_template.md).

На что смотреть: понятна ли проблема, нет ли в решении лишнего, можешь ли ты сам проверить критерии
и нет ли в «Вне рамок» того, что тебе на самом деле нужно.

## 4. Как ревьюить код, если не знаешь Rust

Важно: завершение review в этом проекте считается по действию **Send Feedback** в Plannotator, а не по сообщению «готово» в чат. Если агент не отреагировал автоматически, вернись в ту же сессию и напиши: `обработай feedback из Plannotator по T-XXX`. Для code review локальный fallback-файл: `.reviews/T-XXX-code.json`.

- Сначала читай **отчёт** `docs/reports/T-XXX.md`: что сделано, объяснение по каждому файлу,
  как проверить руками, результаты проверок. Шаблон: [`docs/reports/_template.md`](reports/_template.md).
- Каждая Rust-функция обязана иметь комментарий `///` на русском: что делает, зачем, что принимает,
  какие ошибки возможны, какие проверки безопасности делает. Нет комментария — это блокер, оставь замечание.
- Непонятное место — выдели строку в Plannotator и задай вопрос («зачем это?», «что будет, если файла нет?»).
  Агент ответит и при необходимости улучшит комментарий или код.
- Обязательно пройди «Как проверить руками» из отчёта в запущенном приложении (`pnpm tauri dev`).

## 5. Как не делать задачу бесконечно

- **Финиш проекта** — [`docs/mvp-done.md`](mvp-done.md). Всё, чего там нет, — не MVP.
- **Backlog заморожен.** Агенты не добавляют задачи. Идеи и «было бы хорошо» записываются одной строкой
  в [`docs/later.md`](later.md); переносишь в backlog только ты.
- **Задача готова, когда выполнены её критерии приёмки** — без полировки и рефакторинга «заодно».
- **Лимиты:** план не больше 10 файлов и 120 строк, иначе агент предлагает разбить задачу.
  Не больше 2 кругов правок на каждом ревью — дальше агент задаёт тебе один конкретный вопрос.
- **Застрял:** одна и та же ошибка дважды → агент пишет `docs/handoff.md` и останавливается.
  Ты запускаешь задачу у более сильной модели в новой сессии (MiniMax → Kimi → Claude).

Если чувствуешь, что задача разрастается, — отклони план с замечанием «сократить до критериев X и Y».

| Skill            | Когда работает                                                                                                    | Как гарантируется                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `caveman` (lite) | Все ответы агента в чате — коротко                                                                                | Первый шаг каждой команды `/task-*`. Планы и отчёты пишутся обычным языком |
| `plannotator`    | Ревью плана и ревью кода                                                                                          | Готовые команды запуска внутри `/task-plan` и `/task-build`                |
| `tdd`            | Логика в `src/domain/` и Rust                                                                                     | Указан в `/task-build`                                                     |
| `tauri-v2`       | Работа с конфигом, командами и правами Tauri                                                                      | Указан в `/task-build`                                                     |
| `grilling`       | Интервью перед планом для задач C и задач с неясными решениями — без лимита вопросов, пока не закрыты все решения | Шаг 2 в `/task-plan` (там же правила)                                      |

## 7. Экономия токенов

- **caveman** сокращает ответы агента (выходные токены).
- **RTK** сжимает вывод команд — тесты, `cargo`, `git`, линтеры (входные токены). Подключается хуком
  в Claude Code и плагином в OpenCode; агенту ничего делать не нужно. Если нужен полный, несжатый вывод — `rtk proxy <команда>`.
- Проверить экономию: `rtk gain`.
- **CodeGraph** — граф кода (TS + Rust) для поиска «где X / кто вызывает Y / что сломается». Агент
  использует его вместо grep и чтения многих файлов. **Repowise** — история и риски файлов
  (частые правки, связанные изменения, мёртвый код); используется в планах (раздел «Риски») и на ревью.
  Правила — раздел «Code intelligence» в `AGENTS.md`. Индексы обновляются сами
  (Repowise — git-хуком после коммита, CodeGraph — фоновым процессом); в git они не попадают.
