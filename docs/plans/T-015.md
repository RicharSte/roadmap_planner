# T-015: Windows build (`.msi`/`.exe`)

Статус: approved

## Проблема

MVP не закрыт: `docs/mvp-done.md` требует Windows-сборку (`.msi`/`.exe`), сейчас она не
подтверждена ни разу. Это последний незакрытый пункт раздела «Сборка и передача» —
без него MVP не считается готовым (handoff T-015).

## Решения из интервью

- Способ сборки: **локальная Windows-машина** пользователя (не GitHub Actions, не
  кросс-сборка с macOS — последняя отклонена ещё в handoff T-014→T-015).
- Windows-машина у пользователя уже есть и готова — отдельная инструкция по созданию VM
  (UTM/Parallels) не нужна.
- Подпись/нотаризация, CI, автообновление — не в этой задаче (см. «Вне рамок»).

## Решение

Чек-лист предустановки + сборка `pnpm tauri build` прямо на имеющейся Windows-машине
пользователя, ручная проверка результата (установка, запуск, базовый сценарий), затем
обновление README и отметка пункта в `docs/mvp-done.md`. Агент не может запустить Windows
сам — все шаги сборки/проверки выполняет пользователь по инструкции и подтверждает
результат в чате; агент (на этапе build) обновляет документацию и, если нужно, чинит
платформенные баги в уже существующем Rust-коде (без новых зависимостей/permissions).

Отклонённые альтернативы: GitHub Actions (нет готового workflow, это пересекается с
T-108) — отклонено пользователем; кросс-сборка с macOS — отклонена ранее (handoff),
Tauri 2 её официально не поддерживает.

## Критерии приёмки

- [ ] На Windows-машине `pnpm install && pnpm tauri build` завершается без ошибок
- [ ] `pnpm test` и `cargo test` проходят на Windows-машине (не только на macOS)
- [ ] `src-tauri/target/release/bundle/` содержит `.msi` и NSIS `.exe`
- [ ] Установка/запуск: SmartScreen-предупреждение ожидаемо (неподписанная сборка,
      «Подробнее» → «Выполнить в любом случае»), приложение открывается
- [ ] Ручной сценарий на Windows: создать проект в пустой папке → появились
      `roadmap.json` и `descriptions/`; открыть существующий проект выбором папки
- [ ] `README.md` содержит раздел «Как собрать и запустить на Windows»
- [ ] `docs/mvp-done.md`: пункт «Windows: сборка `.msi`/`.exe`» отмечен `[x]`

## Файлы

- `README.md` — изменить — добавить раздел сборки/запуска под Windows (по аналогии с
  существующим macOS-разделом)
- `docs/mvp-done.md` — изменить — отметить чекбокс Windows-сборки
- `docs/backlog.md` — изменить — статус T-015 → `done`
- `docs/reports/T-015.md` — создать — отчёт по шаблону `_template.md`
- `docs/handoff.md` — изменить — следующий шаг после закрытия MVP-блокера

Исходный код (`src-tauri/`, `src/`) трогаем только если сборка/тесты на Windows
реально упадут из-за платформенной специфики (см. «Риски») — заранее в план не
включаем, это не предусмотренное изменение, а условный фикс бага.

## Шаги

1. На Windows-машине проверить/поставить: Rust-таргет под архитектуру машины
   (`rustup target add x86_64-pc-windows-msvc`, на ARM64 — `aarch64-pc-windows-msvc`),
   Node.js + `pnpm`, WebView2 Runtime (в Windows 11 обычно уже есть; если нет —
   Evergreen Bootstrapper с сайта Microsoft).
2. Получить код на Windows-машине (клонировать репозиторий, ветка `task_15`),
   `pnpm install`.
3. `pnpm tauri build`.
4. Если сборка/тесты упадут из-за Windows-специфики в `paths.rs`/`atomic.rs`
   (разделители пути, блокировка файла) — чинить на месте без новых
   зависимостей/permissions/capabilities; если фикс требует нового плагина,
   permission, capability или зависимости — остановиться и спросить пользователя
   (правило AGENTS.md).
5. Прогнать `pnpm test` и `cargo test` на Windows-машине.
6. Проверить `src-tauri/target/release/bundle/` — `.msi` и NSIS `.exe` созданы.
7. Установить `.msi` (или запустить `.exe`), подтвердить SmartScreen, открыть
   приложение, пройти сценарий «создать проект» / «открыть проект».
8. Обновить `README.md` разделом сборки под Windows.
9. Отметить `docs/mvp-done.md`, перевести `docs/backlog.md` → `done`, написать
   `docs/reports/T-015.md`, обновить `docs/handoff.md`.

## Тесты

Новых доменных тестов эта задача не добавляет — цель прогнать уже существующие
`pnpm test` / `cargo test` на второй ОС и поймать платформенные расхождения.
Если на шаге 4 найден баг в `paths.rs` (`validate_relative_path`) или `atomic.rs`
(`write_inside`) — добавить к нему regression-тест в соответствующий `*.rs` файл.

## Вне рамок

- Подпись/нотаризация Windows-сборки (`docs/later.md` T-301).
- GitHub Actions / CI (`docs/later.md` T-108) — отдельная задача после MVP.
- Кросс-сборка с macOS (`cargo-xwin` и т.п.) — отклонена, Tauri 2 не поддерживает официально.
- Кастомная иконка, автообновление — не требуются для MVP.
- Retry записи при занятом файле на Windows — уже отмечено как идея в `docs/later.md` (T-006),
  не часть этой задачи; известное поведение `IO_ERROR` из ADR 0011 остаётся как есть.

## Риски и вопросы

- `src-tauri/src/project.rs` — hotspot (96%, растёт), `src-tauri/src/atomic.rs` — hotspot
  (70%, растёт), `src-tauri/src/paths.rs` (52%) — у всех трёх `test_gap: true`
  (нет прямых unit-тестов, только через интеграционные вызовы). `paths.rs::validate_relative_path`
  отмечена как `nested_complexity`/`complex_method` — это функция, которая отклоняет `..`,
  абсолютные пути и т. п.; именно она чувствительна к разнице `/` и `\` на Windows, поэтому
  шаг 5 (прогон тестов на Windows) обязателен, а не формальность. Рефакторинг этих файлов —
  не в рамках этой задачи, записан в `docs/later.md` («Входящие», T-015).
- ADR 0011 уже документирует: на Windows запись в открытый другой программой файл даёт
  `IO_ERROR`, следующее автосохранение повторяет попытку — это ожидаемое поведение, не баг.
- Если ошибка сборки/теста на Windows повторится дважды подряд одним и тем же образом —
  по правилу AGENTS.md («Same error fails twice») останавливаемся и пишем `docs/handoff.md`,
  не угадываем дальше.
