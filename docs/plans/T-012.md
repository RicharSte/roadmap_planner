# T-012: Перезагрузка проекта с диска; защита от перезаписи при битом `roadmap.json`

Статус: approved

## Проблема

Пользователь может изменить файлы проекта снаружи приложения (вручную поправить `roadmap.json`
или `.md`-описание). Сейчас единственный способ это увидеть — переоткрыть проект через «Открыть
папку…», что сбрасывает выбор и свёрнутые ветки. Backend (`reload_project` / `reloadProject`, T-005)
уже готов, но ничего в UI его не вызывает. Риск из T-005: если после неудачной перезагрузки
(`roadmap.json` стал битым) пользователь продолжит редактировать дерево или описание, обычное
автосохранение перезапишет диск валидным JSON из памяти и скрыло бы повреждение файла.

## Решения из интервью

- Выбранная нода и свёрнутые ветки сохраняются после успешной перезагрузки, если нода осталась в
  дереве (иначе выбор снимается); `collapsed` — пересобирается, оставляя только существующие id.
  Отличие от «Открыть папку…», где выбор и свёрнутые ветки всегда сбрасываются (это новый проект).
- Если перезагрузка вернула ошибку (`INVALID_JSON`, `INVALID_PROJECT` и любой другой код ошибки
  reload) — блокируется **вся** запись на диск: и `roadmap.json` (создание/переименование/
  перемещение/статус/удаление ноды), и файлы описаний (автосохранение, создание описания).
  Разблокировка — только следующей успешной перезагрузкой.
- Перед перезагрузкой черновик описания (если есть несохранённые правки) сохраняется
  автоматически (`flush()`), без вопроса пользователю; диалог подтверждения (как при закрытии
  окна, ADR 0014) не используется.

## Решение

- `useProject`: новая функция `reload()` вызывает `reloadProject()` (уже существует).
  - Успех — обновляет `project`, пересчитывает `selectedId`/`collapsed` по правилам выше, чистит
    `saveError` и флаг блокировки.
  - Ошибка — сохраняет её в новое поле `reloadError` (отдельно от `error`, у которого другой текст
    и назначение — ошибка открытия) и выставляет `locked = true`.
  - `update()` (и `createDescription`/`saveDescription`) в начале проверяют `locked`: если true —
    возвращают `false`/не пишут на диск, не трогая `reloadError` (баннер должен остаться видимым,
    пока не пройдёт успешная перезагрузка).
- `App.tsx`: кнопка «Перезагрузить» в тулбаре рядом с «Открыть папку…», disabled при
  `project === null`. Обработчик: сначала `descriptionEditorRef.current?.flush()`, затем
  `reload()`, затем увеличивает `reloadToken` (независимо от результата reload — описание может
  быть изменено снаружи даже если `roadmap.json` в порядке). Баннер `reloadError`/`locked` — в
  стиле существующих `error-banner`, текст отличается от баннера открытия. `hasUnsavedRef`
  (ADR 0014) дополняется условием `|| locked`, чтобы закрытие окна тоже предупреждало.
- `DescriptionEditor`: оборачивается в `forwardRef`, через `useImperativeHandle` отдаёт `{ flush }`
  (уже есть внутри как `useCallback`). Получает новый проп `reloadToken: number`; эффект загрузки
  описания добавляет его в зависимости, чтобы перечитать файл даже если `path` не изменился.
- `DetailsPanel`: принимает и прокидывает `descriptionRef` и `reloadToken` в `<DescriptionEditor>`
  без собственной логики.
- Rust/backend не меняются — `reload_project` и `ProjectState::reload` готовы с T-005.

Альтернатива «показывать confirm() перед reload, как при закрытии окна» отклонена пользователем —
выбран автоматический flush без диалога.

## Критерии приёмки

- [ ] Кнопка «Перезагрузить»: disabled, когда проект не открыт.
- [ ] Успешная перезагрузка обновляет дерево; выбранная нода остаётся выбранной, если она есть в
      новом дереве, иначе выбор снимается; `collapsed` не содержит удалённых id.
- [ ] Перезагрузка с несохранённым черновиком описания сначала сохраняет его (`writeDescription`
      вызван с актуальным содержимым), затем выполняет reload — без диалога подтверждения.
- [ ] Битый `roadmap.json` на диске → `reloadProject` возвращает ошибку, баннер показан, файл на
      диске не тронут (ничего, кроме чтения, не вызывается).
- [ ] После ошибки reload: попытка переименовать/переместить/создать/удалить ноду или
      автосохранение описания не вызывает `saveProject`/`writeDescription` — пока не пройдёт
      успешная перезагрузка.
- [ ] Изменение `.md`-файла снаружи при открытом описании → после «Перезагрузить» редактор
      показывает новое содержимое (ручная проверка, подтверждает пункт `mvp-done.md`).
- [ ] `pnpm test`, `pnpm typecheck`, `pnpm lint`, `cargo test`, `cargo clippy -- -D warnings`
      проходят без изменений в `src-tauri/`.

## Тесты

- Успешная перезагрузка: дерево обновилось, выбор сохранён (нода осталась) / снят (нода удалена).
- Reload с `INVALID_JSON`/`INVALID_PROJECT`: баннер показан, `saveProject` не вызван далее при
  попытке редактирования.
- После успешного reload блокировка снята: повторное редактирование снова вызывает `saveProject`.
- Reload с несохранённым описанием: `writeDescription` вызван до `invoke("reload_project")`
  (порядок вызовов), диалог `window.confirm` не вызывается для reload.
- Кнопка disabled без открытого проекта.

## Вне рамок

- Отслеживание файлов в реальном времени (ADR 0002/0010, пост-MVP).
- Разрешение конфликтов — остаётся «последний пишущий побеждает» (ADR 0002/0011).
- Визуальное отключение кнопок дерева/панели во время блокировки — только баннер и отказ записи.
- Русские тексты ошибок общего вида — T-013; текст баннера reload — минимальный, не весь каталог.

## Риски и вопросы

- `src/ui/useProject.ts` — риск-индекс (Repowise) `hotspot_score = 0.88`, `is_hotspot = true`.
  `hotspot_score` — комбинация частоты изменений файла (churn) и его сложности/размера; выше —
  выше риск внести регрессию при правке. `is_hotspot` — булев флаг: score перешёл порог, файл уже
  в списке самых рискованных в репозитории (рядом с `src-tauri/src/project.rs`, `App.test.tsx`,
  `tree.ts`). Функция `useProject` отмечена биомаркером `large_method` (severity `critical`) и
  `complex_method` (`high`) — она и так самая большая/сложная функция в хуке, добавлять новую
  логику аккуратно, не трогая существующие ветки `update`/`applyResult`.
  `src/App.tsx` — `hotspot_score = 0.68` (`is_hotspot` пока `false`, но `trend: increasing`),
  функция `App` тоже `large_method` (impact 0.96). Задача в `docs/later.md` на разбивку обоих
  файлов добавлена ([T-012] в разделе «Входящие»).
- Предложение зафиксировать ADR 0015 для правила «любая ошибка reload блокирует всю запись до
  следующего успешного reload»: это новый тип состояния приложения — не разовое предупреждение
  (как в ADR 0014), а длящаяся блокировка записи, про которую должны знать все будущие фичи,
  пишущие на диск (T-013 «понятные ошибки», будущие «недавние проекты»/автооткрытие). Не
  конфликтует с ADR 0014: тот ADR остаётся про `hasUnsavedRef`/подтверждение закрытия окна
  (используется и расширяется — `locked` добавляется в тот же OR); новый ADR фиксирует отдельный,
  более сильный механизм (блокировка `invoke`, а не просто диалог), чтобы T-013 или следующая
  задача не придумала второй способ «не дать перезаписать битый файл» и не обошла этот стороной.
  Решает пользователь на ревью — если не нужен, достаточно описания в этом плане.
