# Later (после MVP)

План релизов после MVP и входящие идеи. Пока MVP не закрыт (`docs/mvp-done.md`), ничего отсюда
не реализуется. В `docs/backlog.md` задачи переносит только пользователь.

Агенты только добавляют строки в раздел **«Входящие»** в конце файла.
Формат: `- [T-XXX] кратко — почему может понадобиться`

## Карта релизов

| Релиз   | Тема                                 | Формат `roadmap.json` | Агенты                                         | Сеть              |
| ------- | ------------------------------------ | --------------------- | ---------------------------------------------- | ----------------- |
| **MVP** | Редактор дерева + Markdown           | `version: 1`          | нет                                            | нет               |
| **1.1** | Зависимости и блокеры (для человека) | `version: 2`          | нет                                            | нет               |
| **1.2** | Roadmap как пайплайн для агентов     | `version: 3`          | внешние агенты через файлы, без своего runtime | нет               |
| **2.0** | B2C: публичный продукт               | `3+`                  | решается отдельно                              | решается отдельно |

Правила:

- Номер релиза приложения и номер формата — разные вещи. Связь только по таблице выше.
- Каждый релиз закрыт своим «Готово, когда». Следующий релиз не начинается, пока не закрыт предыдущий.
- Схема форматов v2/v3 — ADR 0010 (статус `proposed`, принять перед T-102).
- ID задач: `T-1xx` = 1.1, `T-2xx` = 1.2, `T-3xx` = 2.0. MVP остаётся `T-000…T-015`.

## 1.1 — Зависимости и блокеры

**Цель:** человек видит, что можно делать сейчас, что ждёт другую работу и что заблокировано.
Агентов нет. Это фундамент для 1.2: без зависимостей пайплайна не бывает.

### Что входит

- Зависимости `dependsOn` отдельно от иерархии (иерархия = структура, зависимости = порядок работы).
- Ручной блокер с причиной (`blocker.reason`).
- Вычисляемая готовность ноды (не хранится в JSON):
  `done` → `blocked` → `waiting` → `active` → `ready` (порядок проверки, первый подходящий).
- UI: секция «Зависит от» в панели деталей, поле «Блокер», бейджи готовности в дереве,
  фильтр «Готово к работе / Ждёт / Заблокировано».
- Миграция `version 1 → 2` с подтверждением и резервной копией.
- Техдолг из MVP (см. T-101, T-106, T-107).

### Что НЕ входит

- Агенты, `assignee`, артефакты, отчёты о запусках — это 1.2.
- Новые статусы. Набор `unstarted | in progress | paused | done` остаётся. «Заблокировано» — вычисляемое
  состояние, а не статус.
- Несколько родителей в иерархии (граф иерархии). Потребность в графе закрывается `dependsOn`.
- Холст-граф (ADR 0004) — после 1.2.
- `kind` (task/milestone/note) — осознанно отложено: в 1.1 не даёт поведения, в 1.2 исполнимость
  задаёт `assignee`.

### Формат v2 (кратко, полностью — ADR 0010)

```json
{
  "version": 2,
  "rootIds": ["n_a"],
  "nodes": {
    "n_b": {
      "id": "n_b",
      "title": "Login form",
      "childrenIds": [],
      "status": "unstarted",
      "descriptionPath": null,
      "dependsOn": ["n_x"],
      "blocker": { "reason": "Ждём доступ к API", "since": "2026-11-02T09:00:00Z" },
      "createdAt": "2026-10-13T10:00:00Z",
      "updatedAt": "2026-11-02T09:00:00Z"
    }
  }
}
```

- `dependsOn: string[]` — id нод, которые должны быть `done`, прежде чем эта нода станет `ready`. Хранится
  только у зависимой ноды (одно место, как `childrenIds` в ADR 0005).
- `blocker: { reason: string, since: string } | null`.
- Вычисление готовности: `done` если `status = done`; `blocked` если `blocker ≠ null`; `waiting` если
  хотя бы одна нода из `dependsOn` не `done`; `active` если `status = in progress`; иначе `ready`.

## 1.2 — Roadmap как пайплайн для агентов

**Цель:** roadmap становится контрактом выполнения для внешних агентов (Claude Code, OpenCode и любых
других). Агенты понимают, что готово к запуску, что брать на вход, что сдать на выход и куда
сообщить о результате или блокере. Приложение **не запускает** агентов и не ходит в сеть.

### Ключевые решения

- **Один писатель `roadmap.json` — приложение.** Агенты никогда не правят `roadmap.json` и
  `descriptions/`. Они пишут только в `artifacts/<nodeId>/` и `runs/<nodeId>/`.
- **Человек в контуре.** Отчёт агента не меняет статус сам. Пользователь нажимает «Принять» → `done`.
- **Синхронизация — ручная перезагрузка** (как в MVP). Слежение за файлами — после 1.2.
- Нода исполнима агентом, если у неё `assignee = "agent:<role>"`.

### Папка проекта в 1.2

```
<project>/
  roadmap.json               # структура; пишет только приложение
  descriptions/<id>.md       # описания; пишет только приложение
  AGENTS.md                  # правила для агентов; генерирует приложение (спрашивает перед перезаписью)
  agents/<role>.md           # инструкции роли; редактируются в приложении
  briefs/<nodeId>.md         # задание для агента; генерирует приложение, перезаписывается
  artifacts/<nodeId>/...     # результаты работы; пишут агенты или человек
  runs/<nodeId>/<runId>.json # отчёты агентов; приложение только читает
```

Папки создаются лениво — только когда нужны. Проект без агентов выглядит как в 1.1.

### Формат v3 (кратко, полностью — ADR 0010)

Новое на верхнем уровне:

```json
"agents": {
  "researcher": { "title": "Researcher", "instructionsPath": "agents/researcher.md" }
}
```

Новое в ноде:

```json
"assignee": "agent:researcher",
"inputs":  [{ "fromNodeId": "n_x", "outputId": "spec" }],
"outputs": [{ "id": "spec", "title": "Спецификация", "path": "artifacts/n_b/spec.md" }],
"acceptedRunId": null
```

- `assignee: null | "human" | "agent:<role>"`, роль должна быть в `agents`.
- `outputs[].path` — только внутри `artifacts/<свой nodeId>/`.
- `inputs[]` ссылаются только на `outputs` нод из своего `dependsOn` → поток данных совпадает с порядком.
- Критерии готовности — раздел `## Готово, когда` в `descriptions/<id>.md` (не в JSON).
- `acceptedRunId` — какой отчёт пользователь принял.

Отчёт агента `runs/<nodeId>/<runId>.json`:

```json
{
  "format": "roadmap-run/1",
  "runId": "r_20261120T101500Z_k3",
  "nodeId": "n_b",
  "agent": "agent:researcher",
  "state": "succeeded",
  "startedAt": "2026-11-20T10:15:00Z",
  "finishedAt": "2026-11-20T10:42:00Z",
  "summary": "Коротко, что сделано",
  "outputs": [{ "id": "spec", "path": "artifacts/n_b/spec.md" }],
  "blockerReason": null,
  "error": null
}
```

`state ∈ running | succeeded | failed | blocked`. При `blocked` приложение предлагает (кнопкой) поставить
блокер ноде с `blockerReason`.

### Рабочий цикл 1.2

1. Пользователь назначает ноде роль агента и описывает `outputs`.
2. Ноды с `assignee = agent:*` и готовностью `ready` попадают в очередь «Готово для агентов».
3. «Подготовить задание» → приложение пишет `briefs/<nodeId>.md`: цель, описание, критерии, пути входов,
   ожидаемые пути выходов, файл инструкций роли, куда и в каком формате писать отчёт.
4. Внешний агент читает `AGENTS.md` + brief, пишет `artifacts/` и отчёт в `runs/`.
5. Пользователь жмёт «Перезагрузить» → видит отчёт в панели ноды, наличие файлов-выходов проверено.
6. «Принять» → `status = done`, `acceptedRunId = runId` → зависимые ноды становятся `ready`.
   «Отклонить» → статус не меняется.

Оркестрацию «всего графа» может делать внешний агент-оркестратор: он читает `roadmap.json` (по JSON Schema),
берёт `ready`-ноды и раздаёт их исполнителям. Приложению для этого ничего дополнительно не нужно.

### Что НЕ входит в 1.2

- Встроенный запуск агентов, API-ключи, сетевые вызовы LLM.
- Автозапуск зависимых нод, ретраи, таймауты, approval-гейты сверх «Принять/Отклонить».
- Автоматическая смена статуса по отчёту агента.
- Слежение за файлами в реальном времени.

- [ ] Агент, следуя только `AGENTS.md` + brief, не трогает `roadmap.json` и `descriptions/`.
- [ ] Отчёт `succeeded` виден после перезагрузки; «Принять» делает ноду `done`, следующая становится `ready`.
- [ ] Отчёт `blocked` → кнопка ставит блокер с причиной из отчёта.
- [ ] Битый или чужой файл в `runs/` → понятное сообщение, проект открывается.
- [ ] Выход вне `artifacts/<nodeId>/` отклоняется валидацией.
- [ ] Приложение не делает сетевых запросов (проверка capabilities).

## После 1.2 (не запланировано, каждое — через ADR)

- Холст с графом как второй режим просмотра (ADR 0004); показывает и иерархию, и `dependsOn`.
- Встроенный запуск ноды агентом: нужна сеть, хранение ключей (Keychain/Credential Manager) — противоречит
  текущему правилу «без сети», только через ADR.
- Автозапуск зависимых нод по готовности, ретраи, таймауты, approval-гейты.
- Слежение за `runs/` в реальном времени вместо ручной перезагрузки.
- Несколько родителей в иерархии (граф иерархии, ADR 0005) — только если `dependsOn` окажется мало.
- `kind` ноды (milestone/note), если появится поведение, которое от него зависит.

## Входящие

Сюда агенты добавляют новые идеи и техдолг. Пользователь раскладывает их по релизам.

- [T-002] Покрытие (`@vitest/coverage-v8`), git-хуки, линт Markdown в `docs/`, правила стиля сверх recommended,
  типовой линтинг (`recommendedTypeChecked`) — частично закрывается T-108 (CI)
- [T-002] e2e-тесты запрещены ADR 0007; приёмочные тесты бизнес-логики остаются в домене (T-004+)
- [T-006] Конфликты с внешними правками — принят last-writer-wins, но можно добавить детекцию и ручное разрешение
- [T-006] Retry записи на Windows, когда целевой файл занят другой программой — сейчас сразу `IO_ERROR`
- [T-006] Копирование xattr, Finder-тегов, ACL и владельца при атомарной записи — сейчас теряется
- [T-011] Предупреждение при закрытии приложения с несохранёнными правками из-за занятости файла
- [T-008] Навигация по дереву стрелками (ARIA `tree`) — ADR 0004 называет клавиатуру желательной
- [T-008] Ресайз сайдбара с клавиатуры (`role="separator"`, стрелки ←/→) — доступность
- [T-008] Запоминать ширину сайдбара между запусками — удобство; делать вместе с настройками/недавними проектами (T-107)
- [T-008] Пользовательские статусы и назначение им цвета из фиксированной палитры — brief относит свои статусы
  к out of scope MVP; нужен новый формат `roadmap.json` и ADR
